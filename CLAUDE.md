# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SIA WORLD: a set of browser games behind one login, served as a static site on GitHub Pages with Supabase (Postgres + Realtime + Edge Functions) as the backend. All user-facing text is Korean. Visual design must follow `DESIGN.md` and the shared tokens in `shared/theme.css` / `shared/theme.js` (edit both together).

## Layout

- `index.html` — login + lobby (no build step). Game list, per-game open/closed flags and online counts.
- `shared/*.js` — plain ES modules (auth, supabase client, games list, wallet, room, presence, ranking dialog, sound, zodiac art).
  `shared/characters.js` holds characters outside the 12 zodiac (고양이 `cat`). It is unlocked **per game** for 100 시아코인 from that game's character-select screen (마을: 13번째 주민), only after that game's progress condition (each game migration defines `_cat_progress_<game>(uuid)` → `{have, need}`; play counts for games without records go to `character_play_counts` via `_count_play`) (`buyCharacter(game, id)` → `buy_character`, `071_characters.sql`); the lobby only introduces it. Card games keep using the 12 in `shared/zodiac.js` (화투 12달). Game start RPCs check characters with `_check_character(user, id, game)` ('bad character' / 'locked character'); a new character-select game must do the same, add its id to `_character_games` / `CHARACTER_GAMES`, define `_cat_progress_<game>`, and show the lock + buy button via `loadOwnedCharacters(game)`. **Loaded at runtime by every game, not bundled**, so all games share one login session. A change here affects every game.
- Separate Vite + TypeScript packages, each with its own `package.json`, `node_modules` and tests:
  - `games/` — 맞고 and 카지노 (poker, holdem, blackjack, roulette). Shared shell in `games/lib/`.
  - `games/tank`, `games/running` (dev port 5290), `games/volleyball` (5291), `games/survival` (5292), `games/defense` (5293), `games/village` (5294), `games/charge` (5295, 시아돌격대).
  - `games/finger` (5296) — 시아핑거, 1인 턴제 튕기기 RPG. Simulation in `supabase/functions/_shared/finger/` (shared with the `finger-finish` Edge Function, which re-plays the submitted inputs), SQL in `067_finger.sql`.
  - `games/twelve` (5297) — 시아열두길, 1인 실시간 액션 RPG (12지형 × 8맵 · 장비 · 끝없는 탑; 12지형 + 최종보스맵 `final`(열쇠 12개)까지 열림 — 보통 모드 엔딩·고양이 구매, 그 뒤 어려움 모드(같은 96맵 + `final`, Lv66~99 · `twelve_set_mode`)와 진짜 엔딩까지). Fixed-timestep simulation in `src/game/sim.ts`; maps finish through `twelve_start` / `twelve_finish` and the tower through `twelve_tower_start` / `_floor` / `_end`, all in `078_twelve.sql` (the server recomputes exp · 엽전 · drops from kill counts and the run seed). 078 is live: the data tables (map rows, levels, items, …), `twelve_start` (final map needs 12 keys, hard mode needs the normal final cleared), `twelve_finish` and `_twelve_region_open` are redefined by `094_twelve_full.sql` with `create or replace`, which also adds `twelve_set_mode`.
  - `games/tower` (5298) — 시아의탑, 1인 탑뷰 도트 액션 RPG (character creation → floors 1~100, wish-orb ending). Combat runs on the device; the server only keeps the progress JSON through `tower_state` / `tower_set_look` / `tower_save` (`104_tower.sql`, latest definitions in `106` / `107`). Floor · room · enemy · orb data in `src/data`.
  - `games/pang` (5299) — 시아팡팡, 1인 3매치 퍼즐 (정령 9종 · 특수 블록 · 얼음/상자/덩굴 · 100스테이지). Plain-JS engine `src/game/engine.js` (also used by the balance scripts); the server only records runs and per-stage stars/best through `pang_state` / `pang_start` / `pang_finish` (`111_pang.sql`, stars recomputed from the score with `_pang_stages`). Stages are generated by `scripts/levelgen.mjs` and tuned by `npm run levels` (autopilot, minutes long) into `src/data/levels.json`; `npm run sqlrows` rewrites the `-- <gen:stages>` block in 111 and `tests/sql.test.ts` checks it. Dev: `?local=1` (+ `&all=1`).
- `supabase/migrations/NNN_*.sql` — numbered migrations (currently up to 111; check `ls supabase/migrations` before adding one).
- `supabase/functions/_shared/` — card-game rule engines and round runner; `game-action` and `game-timeout` are the card-game Edge Functions; `finger-finish` (시아핑거) re-plays a run with `_shared/finger/`.
- Each newer game keeps its spec in `games/<name>/PRD.md` and art notes in `ASSETS.md`.

## Commands

Run inside the package directory (`games`, `games/tank`, `games/running`, `games/volleyball`, `games/survival`, `games/defense`, `games/village`, `games/charge`, `games/finger`, `games/twelve`, `games/tower`, `games/pang`):

```bash
npm run dev            # Vite dev server
npm test               # vitest run
npm run build          # tsc --noEmit && vite build
npx vitest run <file>  # one test file;  add  -t "<name>"  for one test
```

- In `games/`, vitest's root is `supabase/functions/_shared` (see `games/vitest.config.ts`): the rule-engine tests live there, e.g. `cd games && npx vitest run matgo.test.ts`.
- `games/survival`: `npm run balance -- <runs> [dps|chars|maps|endless] [map,map]` runs the balance sweep (9 worker processes, minutes long). `games/tank` has `npm run balance` / `stats`.
- `games/defense`: `npm run balance -- <runs> [towers|stages|levels|chars|endless|journey] [region]` runs the balance sweep (minutes long). Stage data `src/data/stages/r02~r12.ts` is generated by `scripts/gen-stages.ts`; coin values are mirrored in `048_defense.sql` (`scripts/sql-stages.ts`, checked by `tests/sql.test.ts`).
- `games/finger`: `npm run calib` re-tunes stages 2~12 with the autopilot (9 worker processes, minutes long) and `npm run gen` rewrites `_shared/finger/stages-gen.ts`; `npm run tower` measures how high the autopilot climbs the endless tower per level; `npm run sqlrows` prints SQL rows, and `tests/sql.test.ts` checks `067_finger.sql` against `src/data`. Dev: `?local=1` (+ `&all=1`, `&auto=1`, `&stage=`, `&speed=`).
- `games/twelve`: balance numbers live in `src/data` (`economy.ts`, `growth.ts`, `tower.ts`, …) and the tables between `-- <gen:name>` markers are written by `npm run sqlgen` into the file holding each table's latest definition (`blockFile` in `src/data/sqlrows.ts`: the map table `_twelve_maps` in `109_twelve_short_maps.sql`, the rest in `094_twelve_full.sql`; 094 is live and its old `maps` block stays as is) — never by hand; `tests/sql.test.ts` compares 078 + 094 + 109 (the last definition of each function). `npm run gen` regenerates the map files `src/data/maps/r01~r12.ts`, `npm run pace` prints the play-time / level curve with the autopilot (normal + hard, ~4 minutes; `-- 12` normal only, `-- hard` hard only from a `PACE_CACHE` folder, `-- weapons` compares the four weapons), `npm run tower` shows how high the autopilot climbs the endless tower. The rules exist twice — `src/game/progress.ts` · `drops.ts` · `rules.ts` · `tower.ts` and the SQL RPCs — and `scripts/pg-expect.ts` + `scripts/pg-check.mjs` run both against PGlite step by step (PGlite is not in the repo: install it in any folder, see `games/twelve/PROGRESS.md`). Dev: `?local=1` (+ `&map=1-3`, `&lv=`, `&god=1`, `&all=1`, `&hero=`, `&weapon=`, `&mode=hard`).
- `games/village`: all resource changes are server RPCs computed with server time (`047`, `049`–`054`); the same rules live in `src/game/rules.ts` for local mode and preview, and `tests/sql.test.ts` checks the SQL tables against `src/data`. `npm run pace` simulates the growth curve, `npm run sqlrows` prints SQL rows from the data files.
- `?local=1` on a dev server (localhost only) runs 레이스/배구/서바이벌 without login or Supabase. Survival also accepts `?t=<sec>`, `?mode=endless`, `?cleared=<maps>`.
- There is no Deno on the dev machine; engine code is tested through Node/vitest only.

## Deploy

Pushing to `main` runs `.github/workflows/deploy.yml`: test + build every package → `supabase db push` (**runs new migrations against production**) → deploy the Edge Functions (game-action, game-timeout, finger-finish) → publish Pages. A failing test in any package blocks the whole deploy. Check with `gh run watch`.

Consequences:
- Never edit a migration that has already been pushed; add a new numbered file. Later files redefine functions with `create or replace` — the latest definition wins, so find it before changing a function.
- Migration numbers must be unique and pushed in order; when several changes are in flight, don't push a commit history that contains someone's unfinished migration.
- Client and SQL/Edge Function changes that depend on each other must ship in the same push.

## Architecture notes

### Card games (맞고·카지노)

- An engine implements the `Engine` interface in `_shared/engine.ts`: pure TypeScript, JSON-serialisable state, all randomness through the passed `Rng`, relative imports with `.ts` extensions (Deno rule). The same engine files are imported by the browser.
- `_shared/runner.ts` (`Runner`) loads room/seats/deck through the `Store` interface (`store.ts` = Supabase, tests use an in-memory store), applies actions, plays AI seats, saves with optimistic locking on `game_decks.version`, publishes `game_states.public_state` + per-seat `game_private.hand`, and settles through SQL RPCs (`apply_round_result`, `finish_round`). Clients receive state via Realtime `postgres_changes`.
- pg_cron `cron_tick()` calls `game-timeout` for passed deadlines, left seats, and stuck rooms.
- `games/lib/shell.ts` is the shared table UI for all five card games: room screen, state intake, the replay director (`runQueue`: plays new `events` one step at a time, optional `rewind` frames from `*-rewind.ts`), cut-ins, result box → table cleanup (`tidy`) → ready. Each game supplies a `GameUI` object in its `main.ts`. Changes to the shell must be checked against every game, not just the one being worked on.
- 맞고 runs locally first (`_shared/solo.ts`, `games/lib/solo-play.ts`): state carries `solo: { seed, n }` and `soloStep` makes every step deterministic on server and client. One human + AI: the client plays the whole round and sends only the human actions (`replay`); the server re-plays them, playing the AI itself, and settles. Two humans: each client applies its own action immediately, broadcasts it on the room channel, and sends `act` with `n` in the background; the server stays the referee. Both clients hold the full state (deck and opponent hand) — this trade-off was chosen deliberately by the owner.

### Standalone games

- 탱크, 배구 use Supabase Realtime Presence/Broadcast rooms with a host-authoritative, fixed-timestep simulation kept in pure modules with vitest tests.
- 레이스 is single-player since 2026-11-23 (room play removed): the first screen is 오늘의 도전 (`src/net/solo.ts`, `race_go` → `race_submit` → `race_daily_submit`), me + AI, plus the day's 1st-place ghost replayed from recorded press steps (`src/game/ghost.ts`, `095_race_ghost.sql`, the receiving device re-plays and drops it if off by >10ms). Weekly ranking `096_race_weekly.sql` is filled by a trigger when `race_runs.daily_day` is set. Tiers on the 최고 기록 tab are 1st/2nd/3rd one person each.
- 서바이벌 is single-player: the simulation runs on the device and the server validates results in SQL (`survival_start` / `survival_finish`: elapsed-time check, per-second caps, kill floor, overlap check). The validation constants exist twice — `_survival_const` in SQL and `LIMITS` in `games/survival/src/game/progress.ts` — and `tests/sql.test.ts` reads the migration files to assert they match. A new migration that redefines these functions must be added to the list that test reads.

### 오늘의 도전 (daily)

- 레이스·서바이벌·돌격대·핑거·디펜스: `082_daily.sql` (`daily_scores`, internal `_daily_record` — score is always "higher is better", `daily_today()`, `daily_ranking(game, day)`) + `shared/daily.js` (`dailyTodayStrict` for runs that record to the server, `dailySeed`/`dailyPick` build the day's conditions from the date string on every device). Each game records only from its own server-validated result (083 race, 084 survival, 085 charge, 086 finger, 087 defense); daily runs give no stars/unlocks/stage records. New games join by adding to `_daily_games()` / `DAILY_GAMES`.

### SQL conventions

- State-changing access goes through `security definer` functions with `set search_path`, explicit `revoke`/`grant`, and RLS on tables; clients do not write tables directly.
- Shared economy: `wallets` (게임 화폐 + 시아코인 via `_grant_sia_coin`), `app_settings` (`game_open:<id>` flags, lobby caps), `user_sessions` (one session per account).
- Adding a game means: an entry in `shared/games.js`, a `game_open:<id>` row, a channel in `shared/presence.js` `GAME_CHANNELS`, a ranking tab in `shared/ranking-dialog.js`, build/copy steps in `deploy.yml`, and the PWA head block in its `index.html` (manifest + apple-touch-icon links, theme-color + 3 app metas, `<script type="module" src="…/shared/pwa.js" vite-ignore>` — copy it from `games/tank/index.html`, fixing the relative path).

## Working conventions in this repo

- Commit messages are Korean, conventional-prefix style (`feat(matgo): …`).
- Generated art comes from SpriteCook; asset ids are recorded in each game's `spritecook-assets.json`, and code-drawn fallbacks are kept for when an image fails to load.
- 맞고 runs the same engine on the device and the server: when a rules change makes the same action list produce a different result, bump `MATGO_RULES` in `supabase/functions/_shared/matgo.ts` (older tabs then get a reload prompt).
- Seats a player left mid-hand (`left_game`): the Runner plays them with `engine.leftAction` (blackjack: sit out / stand) or `engine.timeout` when `leftUsesTimeout` (poker, hold'em: check else fold), otherwise AI. Seats that sat out are left out of `settle().deltas`, because `apply_round_result` grants 시아코인 to every seat present in `deltas`.
- Realtime games with a host device (tank): a hidden tab must not stay host — tank marks presence `away`; in the waiting room every device on the room screen sends `touch_room`, and only a visible device on the room screen (`isSweeper`) removes dropped players. Keep this in mind when adding host-only duties.
- PWA: one app for the whole site. `manifest.webmanifest`, `sw.js` (root scope; `__SW_VERSION__` is replaced with the commit hash in deploy.yml, so every deploy installs a new worker and drops old caches) and `offline.html` live at the root; `shared/pwa.js` registers the worker and shows the "새 버전이 있어요" banner and install hints. Pages, `shared/*.js|css` are network-first; hashed assets, images, sounds, fonts are cache-first; Supabase and non-GET requests are never cached. On localhost the worker registers only with `?pwa=1`. Icons: `scripts/make-app-icons.py` → `shared/images/app/`.
